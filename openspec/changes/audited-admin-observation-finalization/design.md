# Audited admin finalization: conditional design, safety gate BLOCKED

**Decision: BLOCKED.** Do not implement or enable admin finalization. Migration 091's `AFTER INSERT` trigger deletes **every** matching draft, including another actor's. A selected-row lock or pre-insert count does not protect an absent competing row. A separate verifier's disposable PostgreSQL 17 *minimal synthetic* proof now demonstrates that the proposed global drafts-table lock stalls unrelated draft traffic and can deadlock with the existing predecessor-row-first revision order. The global table-lock candidate is **UNSAFE AS-IS**; no narrower replacement has been proved. The original coordinator submitting in their own session after the ordinary-form numeric N/A-reason fix, if current assignment and window allow, is a **safe alternative**, not a fallback chosen or approved by the user; the user selected admin safety research. No production submission or data change is authorized by this design.

## Review path and boundaries

1. Review the serialization gate and its PostgreSQL concurrency proof before considering an admin entry point.
2. Review the trusted-session, exact-review, canonical-validation and provenance contracts.
3. Require tests, Preview environment evidence and **new explicit human approval** before any production change; neither this document nor earlier approval authorizes deployment or finalization.

Scope: `src/` Astro SSR and `supabase/migrations/`, not `packages/coding-agent`. Seven initial versioned observation definition codes: `observation_escolarizado`, `observation_ejecutivo`, `observation_virtual`, `observation_supervision_clinical`, `observation_professional_practice`, `observation_simulation`, `observation_teaching_competencies`. Traditional Escolarizado v1.2 is versioned and included. Reject unversioned legacy tables, reevaluations and revision drafts (`operation_id`/`supersedes_submission_id` must both be NULL). Do not alter ordinary capture eligibility, permit window/assignment overrides, impersonate the owner or send owner notifications.

**Verified repository facts:** 090 stores mutable actor-scoped drafts under a unique `(submitted_by, docente_id, cuatrimestre_id, version_id)` key; 099 permits separate revision drafts in that table. 091/099 initial autosave can remove only the caller's initial draft when a final exists, but 091's `discard_observation_drafts_on_submission` trigger deletes **all** drafts for the target on *every* observation insert, including revision inserts. 057 makes submissions immutable; 097 restricts the existing observation uniqueness index to `revision_kind = 'initial'`. 064's `submit_versioned_instrument` is the existing initial submission validation/scoring/audit implementation; 092's `BEFORE INSERT` window trigger checks an independently configured observation window. 040's append-only audit is separate from final-row immutability. The ordinary capture component retains a hidden stale N/A reason after a switch to numeric; `/api/instrumentos/submit` currently treats initial unique-conflict lookup by submitter as a retry, which is **not** an acceptable idempotency rule for this admin operation. Live RPC parity is unconfirmed due to the temporary SQL authentication failure (#169); repository SQL alone is not a production attestation.

**Proposed review token:** On save, increment a DB-owned monotonic `draft_revision` (BIGINT, initial 1) for every initial draft write, including byte-identical saves. Preview returns a server-issued short-lived operation UUID and an opaque authenticated, expiry-bound token over actor ID, selected draft ID, owner, target tuple, `draft_revision`, canonical JSONB content SHA-256, active version identity, and a sorted fingerprint of *all* matching draft IDs/owners/revisions/kinds plus current head. Store a bounded pending review record in a restricted table (or signed server-side token with a replay-safe committed receipt); no draft content or teacher identifiers in logs. Confirm receives only operation ID, review token and explicit confirmation, not submitted_by, scores or answers. Bind token/receipt to active actor and selected draft; on confirm re-read selected row and draft set under the proved serialization boundary and compare revision, hash, set fingerprint and target. A changed row, removed row, owner, matching draft set or head forces a fresh preview even if it later changes back; note that fingerprint cannot detect deletion/recreation of an identical row without stable IDs and revisions. Prevent operation UUID reuse with a unique DB constraint and authenticated receipt lookup. A retry may return the prior committed receipt **only** for the same actor, same confirmed operation, exact reviewed revision/hash and target; do authorization before receipt lookup, reject all other payloads/actors and never fall back to the ordinary submit retry lookup. Persist receipt/provenance in a restricted unique `(operation_id)` association referencing immutable final ID and selected draft ID, original owner ID, revision/hash, actual submitter ID and audit event ID. **Score and content:** Preview derives the expected raw and normalized score from the active version's `scale_metadata`, scored items and canonical 064 formula; if the true N/A threshold would mark the result invalid, **reject** rather than show a valid score. Compare preview expected score against the canonical RPC output on confirm, abort on discrepancy. Obtain current/prior result through the authorized versioned score/result path (`versioned_instrument_score_rows` and `calificaciones.ts` scoring behavior), not from cached browser state; label whether the prior observation result is absent or belongs to an older version/head, and disclose that final overall teacher result is recalculated only after commit. Preview is informational and never a promise that downstream aggregate score is already committed. Normalize only by removing `na_reason` from an answer whose JSON `value` is a numeric type; count only **nonblank** stale reasons removed, never change numeric values, evidence, metadata, genuine N/A reasons or other answer fields. Do not silently fix out-of-range values, incomplete item sets, invalid evidence, unsupported subjects/groups, or excessive N/A. Call the current canonical `submit_versioned_instrument` from the admin database transaction under the authenticated superadmin identity (subject to proving the live definition and extending any needed active-instrument rule), passing the stored, normalized draft and an empty observation checklist; `submitted_by` must be `auth.uid()`. The existing RPC does not enforce a group-to-teacher/subject relationship; explicitly validate the requested observation target under existing assignment/subject rules rather than claim this validation already exists. Any additional canonical validation should be shared, not copied into a second divergent submit implementation. For the ordinary capture form, clear hidden N/A text on numeric selection, hydration/save and submit, limited to observation initial capture (verify other forms independently).

## Critical concurrency gate: global-lock candidate disproved as a deployable design

**Required invariant:** For the selected `(docente_id, cuatrimestre_id, version_id)` there is exactly the selected actor's **initial** draft and no other actor's matching initial draft at the serialization point; no other actor's matching draft can be committed before the admin insert and through 091's `AFTER INSERT` cleanup. Treat any other actor's initial draft as a blocker; do not let 091 erase revision drafts either. A nonlocking `SELECT count(*)` or `SELECT ... FOR UPDATE` on currently present drafts cannot block phantom inserts. An advisory lock held only by the new RPC is equally insufficient: existing save/delete/final/revision paths do not take it. `SERIALIZABLE` on one RPC alone does not serialize nonparticipating writers or guarantee the requested fail-closed outcome.

**Local evidence update (not migration proof):** A separate verifier ran `/tmp/admin-draft-lock-proof-20261012/run.sh` on a fresh disposable, UNIX-socket-only PostgreSQL 17 cluster with a **minimal synthetic schema**. Cases A–F passed: an already-committed other-actor draft vetoed admin; a writer queued behind admin waited, then observed the final and did not insert; a writer committed before admin's lock was observed; stale owner revision vetoed; a revision draft vetoed and the unsafe trigger deletion rolled back; and a writer for a **different target** waited at least 100 ms. Case G passed as a counterexample to the candidate's safety: when admin took `SHARE ROW EXCLUSIVE` on the drafts table then sought the predecessor row, while a revision insert held that predecessor row first and its 091-style `AFTER INSERT` cleanup sought the drafts table, PostgreSQL reported **SQLSTATE 40P01** to the writer (one error, no timeout); admin had no error and no partial state remained. Passing G means the fixture successfully exposed the lock-order deadlock, **not** that the candidate is safe. The fixture did not execute the actual 090/091/099/064 migrations, JWT/RLS, audit, production traffic or performance workload. It cannot attest to real-schema behavior or deployment safety. Production remains untouched; Supabase SQL temporary login #169 still blocks live RPC parity.

**Disposition:** Do not adopt `LOCK TABLE public.instrument_submission_drafts IN SHARE ROW EXCLUSIVE MODE` as proposed. It globally blocks even unrelated draft writes and introduces a concrete predecessor-row/table-lock inversion against the 098-style revision path and 091 cleanup. Short timeouts, retries or a new admin-only advisory lock do not establish the required fail-closed non-destructive behavior for all writers. The user-selected policy is: only another actor's draft **already committed before admin obtains serialization** vetoes admin; a later queued writer must receive a completion/conflict without storing a draft. This clarification does **not** approve the global-lock candidate, override the original no-deletion rule, or prove a per-key solution.

**Research gate before any tasks/apply:** Redesign a narrower database-enforced serialization boundary shared by **all** initial-draft writes/deletes, revision-draft writes/deletes, ordinary initial and revision submissions and their 091 cleanup (including privileged/direct write exposure); establish one compatible lock order across predecessor/head, draft and audit locks. Prove committed-before-lock visibility under fresh snapshots, queued-writer post-final guard, selected-draft-only cleanup, unchanged ordinary capture behavior, key-changing updates, phantom exclusion, deadlock/timeout handling and acceptable unrelated-target latency on the **real migrations** with multi-session PostgreSQL 17 fixtures. Do not claim per-key triggers/advisory locks suffice until every path participates and proof passes. 091's unfiltered cleanup also needs a revision-safe policy for ordinary callers. If no safe shared design is demonstrated, remain BLOCKED with no admin grant/UI. The next product decision is either to fund this broader redesign (likely >400 authored changed lines, requiring ask-on-risk chained-slice approval) or for the user to elect the original coordinator route after the form fix; neither decision has been made here.

**Transactional order if unblocked:** authenticate and check approved token; acquire approved serialization boundary before reading target state; verify role, owner assignment, window, active version, selected row revision/hash, draft-set fingerprint and no conflicting final/revision; normalize the stored JSON and validate via canonical RPC; assert returned validity/score; persist unique provenance receipt and append an `admin.observation.finalized` audit event through `audit_write_event` with actor `auth.uid()`, original-owner ID in restricted association, safe identity references and count/hash only (no answers/free text); permit only selected-draft cleanup; commit as one RPC transaction. A failure in canonical validation, trigger, provenance, unique constraint or audit must abort the whole RPC (never catch and continue after destructive steps). If a same-operation response is lost, retrieve the existing receipt without re-inserting. Handle concurrent ordinary initial unique conflict and revision/head conflict as rejection unless the receipt matches exactly. Audit failure is fatal pre-commit; rejected attempts may have separately sanitized operational telemetry, not a misleading committed success event.

**After commit:** API triggers `recalcularCalificacionDocente(dbAdmin(), ...)` once for the committed final; deduplicate warning and operational alert by operation/final ID in a restricted retry/outbox status (not by resubmitting), expose an authorized repair action that recalculates scores only. A recalculation failure leaves the immutable final and its receipt/audit intact; show a recoverable nonduplicate warning. `logRecalcError` currently prints target IDs and raw error: replace/contain it for this flow with bounded error code and correlation ID, never log draft JSON, names, answers, evidence, tokens or raw DB errors. No email or owner notification.

For drafts committed before admin serialization or changed reviewed state, assert **no final, no deleted competing draft, no success audit/provenance**; successful final deletes at most selected draft. A writer queued after admin serialization must not store a draft after final and must receive completion/conflict; unrelated draft traffic must remain acceptably available under load. If any schedule disproves the approved policy, stop rather than weaken it.
- Test full unique item/evidence coverage, per-version integer scale, assignment/group eligibility, active version, missing/closed window, true N/A threshold and reason, five-or-other-count numeric stale reasons and zero-count case; assert exact score/evidence preservation and score discrepancy rejection. Test preview expiry/tampering, updated_at collision versus monotonic revision, content hash, changed draft-set fingerprint and fresh-review requirement.
