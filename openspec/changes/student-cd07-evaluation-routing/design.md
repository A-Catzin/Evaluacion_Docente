# Design: server-bound CD-07 routing without changing general evaluations

**Decision.** Keep the native 19-answer student survey and its historical interpretation. Add a distinct, immutable CD-07 V1.1 contract (20 required integer 1–5 answers only (no N/A, null, blank, `na_reason`, or alternate nonnumeric code) and optional open item 21, at most 2,000 characters), select it only at a trusted student/group/teacher/cycle boundary, and join its valid real-assignment scores to the existing student indicator. TEST-CD is a separate, disabled-by-default fixture exception and is never an institutional source. This is a design, **not** permission to migrate, activate, or write production data.

## Review path and known boundaries

1. Review the authorization/persistence boundary and the source-level score exclusion below.
2. Reconcile the selected 20-assignment CSV roster; review the now-observed schema-only RPC/constraint evidence against the migration ledger, live behavior, full DB consumer inventory and backups before any migration or activation.
3. The user has approved conditional local planning and stacked-to-main review units of at most 400 authored changed lines each; evidence gates below still block affected implementation and activation. This does not authorize production writes or deployment.

## Selection and request contracts

**Trusted routing record (proposed).** An owner-approved, versioned activation manifest maps exact `(cycle_id, group_id, teacher_id, subject_id)` assignment tuples to `CD-07-V1.1`; retain approval provenance, manifest revision/digest and authorization timestamp outside student-readable surfaces. A forward-only DB table with FK to cycle/group (subject/teacher resolved from the current group) and unique `(cycle_id, group_id)` is one option; publishing a signed, independently reviewed server-side registry is another only if the DB RPC validates the same revision at write time. Prefer the DB-backed manifest for a single transactional source of truth. No manifest rows are populated until authoritative roster/27-1 reconciliation yields **exactly 20 distinct real CSV-present active assigned groups**, teacher and subject mappings, cycle identity and approved exclusions; abort on duplicate, unassigned, reassigned or mismatched entries. Recheck group/teacher/subject and enrollment on each read **and** submission; freeze or invalidate affected entries when import/reassignment changes identities. Activation is a separate explicit gate, never a migration side effect. Do not silently route ambiguous groups to the general form: when activation claims CD but mapping cannot be verified, withhold submission and show an unavailable/retry state.

**Listing (proposed).** Extend the student-scoped `obtener_evaluaciones_estudiante_actual` contract or a companion student-scoped RPC to return `instrument_code`, `instrument_version`, `assignment_revision`, `completed` alongside its current safe display fields. The RPC derives authenticated active student identity from `auth.uid()`/`usuarios`, enrolled **assignment** group, active 27-1 cycle and current group teacher/subject; never accepts student ID or teacher identity from the browser. Return `general-19` for ordinary assignments, CD-07 only for a reconciled active real entry, or an explicit unavailable state for a claimed-but-invalid entry. Missing/invalid instrument data must not be dropped by `isEvaluation` and interpreted as general eligibility. `src/lib/studentEvaluations.ts` parses a strict discriminated response and rejects unknown versions; dashboard and `[grupoId].astro` only render the returned assignment and server-selected instrument. Completed status is cross-version. A group URL is a locator, not proof of entitlement; SSR failures display no questionnaire.

**Submission (proposed).** Keep the existing general payload and `EstudianteEvaluacionSchema`/19 prompt order for non-CD assignments; give CD-07 an explicit versioned envelope, e.g. `{grupo_id, instrument_code:'SED-360-INST-EST-CD-07-V1.1', assignment_revision, respuestas:[20 integers], comentario?:string|null}` with a strict Zod discriminator and no client-provided student, teacher, cycle, fixture status, or score. The server-chosen version at commit time overrides the client's claim; stale version/revision returns conflict without writes. A dedicated CD API handler or a discriminated branch in `src/pages/api/estudiante/evaluaciones.ts` may be used only with one shared authorization/persistence policy. Preserve current general HTTP status meanings (`completed` 201, `already_submitted` 409, `no_active_cycle` 409, `not_enrolled` 403, malformed 400), add safe `instrument_unavailable`/`stale_assignment` conflicts; never log body/comment or expose enrollment details. `src/lib/rateLimit.ts` currently checks `Content-Length` only and fails open on DB count errors: bound actual bytes for both formats, and keep rate limiting defense-in-depth, not the one-time invariant. The UI must require all 20 quantitative answers and never offer N/A. Reject N/A, null, blank, `na_reason`, and alternate nonnumeric codes at both API **and** DB type/range boundaries, with no partial effects; validate exactly 20 ordered integers 1–5, exact code/version, no extra fields, and optional item 21 length/moderation at both boundaries. Enforce the CD-07 2,000-character maximum in its new DB path; do not conflate this with the dumped general-RPC 500-character rejection or treat the current UI's 2,000 allowance as a working general DB contract. UI generates CD prompts only from the named draft (not the other five); explicit question ordering/version is immutable after first capture. If text changes, publish a new version.

## Atomic storage and trust boundary

Propose an additive, forward-only migration series (final names/numbers chosen after checking deployed migration history; never change already applied files):

- **Schema/controls:** retain existing `encuesta_estudiantil_respuestas` and `encuesta_control_envio` for historic general records. Add a student-specific CD response table with generated key, cycle/group/teacher/subject IDs, immutable instrument code/version, exactly 20 required integer 1–5 ordered values (JSONB validated by a DB function or integer array with cardinality/range checks; no N/A, null, blank, `na_reason`, or alternate codes), DB-bounded optional comment (2,000 characters), capture timestamp and `real`/`fixture` provenance set only by trusted RPC; no student identifier or direct control-to-response key in the response table. Add FKs/indexes and use the **observed** control unique `(estudiante_id, grupo_id, cuatrimestre_id)` as the intended single cross-version claim after staging validation of the deployed constraint and duplicate state. The legacy response table's checks/FKs are not a substitute for that control. Never create a version-specific uniqueness key that permits two submissions. Dump table grants are broad even with RLS; review effective privileges and explicitly harden direct insert/update/delete for `anon`/`authenticated`, apply RLS to new storage, minimize function grants, and use fixed `search_path` and qualified objects for security-definer functions. Comments/responses available only through authorized privacy-preserving workflows. Do not repurpose `instrument_submissions` (057/058), which has staff purpose/actor policies and no anonymous survey semantics.
- **Transaction/RPC:** preserve the dumped general 19-answer/500-comment contract while modifying or wrapping `enviar_encuesta_estudiante` so even an old 19-answer client cannot submit to a currently CD-assigned group; guard the new versioned CD RPC against old/new cross-version duplicates and enforce its separate DB comment/answer bounds. Under `auth.uid()` verify active `usuarios` role `estudiante`, its unique student entity, active cycle, exact enrolled active assignment group (not base group), teacher/subject matching approved manifest, version/revision and fixture gate where applicable. Serialize competing submissions using a row/advisory lock scoped to student/group/cycle plus the DB unique control; check preexisting controls for both formats, then insert response and control **in one DB transaction**, not two HTTP requests. On uniqueness conflict return `already_submitted` without touching the original; any other error rolls back both and its completion audit. Review the observed legacy signature/body/ACL against live execution and PostgREST cache before choosing a compatibility replacement plus a new RPC; a new RPC alone is insufficient while the old one remains callable. Dump grants to `anon` are not proof of usable anonymous submission, but require explicit privilege review. The app's post-commit `recalcularCalificacionDocente` can fail; do not call that a rollback of the submission. Queue/retry or record a safe pending-recalc signal for an authorized retry, and test reprocessing without duplicating submissions.
- **Audit/privacy:** preserve the existing protected `encuesta_control_envio` completion event if deployed behavior matches the runbook: original `auth.uid()` actor available only in protected audit, no response/comment/student-to-response linkage in UI, report or ordinary log. If the new storage bypasses that trigger, add an equivalent commit-bound protected event. Never attribute later recalc to the student as though it were their original write; preserve provenance. Confirm staff comment tracking permissions, retention and redaction before including new comments; deny by default rather than making TEST-CD or private text queryable through a privileged legacy endpoint.

The data path is **student session → student-scoped assignment resolver → SSR-selected general/CD form → bounded authenticated API → DB-authenticated atomic RPC → versioned response + shared control + protected audit → filtered native score source → score consumers**. Client-supplied group/revision/version only identifies the requested selection and cannot grant eligibility. No application service-role submission, and no silent success if any necessary RPC returns missing or malformed data.

## Fixture is isolated; score exclusion begins at source

TEST-CD is **not** a twenty-first real manifest entry. Design an independent, off-by-default fixture authorization record/gate (not `es_prueba` inferred from a name or active-list visibility). Enabling it requires a separate explicit production write plan approved by the user, verified trusted course/group/teacher identity, authenticated separately verified test student account with matching active enrollment, correct active cycle, and a distinct fixture branch in the same DB trust boundary. Store trusted fixture provenance keyed to approved group/cycle (and teacher/subject), not a request flag; reject unknown or spoofed identity with no writes. The gate remains off before such approval; do not create course/accounts or make submissions in this change. In a permitted fixture-only workflow, completion may be visible to that student, but institutional progress and results must not ingest it.

**Source invariant:** the DB-owned institutional score/progress queries must join each native response/control to a trusted resolved assignment classification, exclude fixture groups **before** computing score, valid count, eligible enrollment denominator, or recalculation input, and reject/raise on unclassified or conflicting provenance. Do not classify a teacher wholesale: a teacher may have both real and fixture groups. Make a version-aware, provenance-bearing `obtener_scores_encuesta_estudiantil_nativa` contract (or reviewed successor) aggregate legacy 19-answer rows with their established `native-19-v2` semantics and new valid real CD rows, grouping at cycle/teacher/subject/group grain; enforce a strict `version_calculo` whitelist in `fetchNativeStudentEvaluationScores` instead of rewriting all results to `native-19-v2`. If the legacy RPC cannot expose enough group identity to prove exclusion, replace/guard it before fixture writes; unknown identity is an error, not an empty list or a dropped row. CD per-response score is `(mean(respuestas) - 1) * 25`, 1→0 and 5→100; average scores weighted by **valid response count**, not number of questions. Do not double-count a response through old and new tables; do not recalculate old answers with a new formula. Establish DB rounding and mixed-version equivalence from deployed evidence before activating.

Audit every institutional consumer, not merely the teacher average: `src/services/scoring.ts` teacher, subject, batch and `fetchSubjectAwareCuatrimestreScores`; `src/services/calificaciones.ts` inline, persisted `calificaciones_finales`, import/recalc and `resultados_agregados` refresh; `src/pages/api/admin/exportar-resultados.ts` group CSV; `src/pages/api/admin/reporte-cuatrimestre.ts`, `src/pages/api/coordinador/reporte-cuatrimestre.ts`, admin/coordinator dashboards and history, `src/pages/docente/materia/[asignaturaId].astro`, `src/pages/admin/instrumentos.astro`, `src/pages/admin/dashboard.astro` progress via `obtener_progreso_encuesta_estudiantil_nativa`, and `src/pages/api/admin/instrumentos/comentarios-estudiantiles.ts` (privileged direct legacy table read). Check DB-side materialized views/other RPCs by authorized inventory. Reports reading persisted scores must use already-filtered calculations; direct native reads use the filtered source; direct raw comment/result queries must filter verified provenance and deny unknowns. Institutionally scoped teacher listings/denominators must not gain fixture-only participation; filter at assignment grain, and do not erase a legitimate teacher's non-fixture result. Throw/503 on missing provenance/schema mismatch; test both cached and fresh results, refresh/recalc paths, raw comments, CSVs and denominators. A client-side filter on `TEST-CD` text or excluding only the export is insufficient.
