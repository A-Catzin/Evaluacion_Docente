Establish backup, reconciliation, deployment and rollback boundaries before any live activation; application rollback cannot undo an already committed schema/data change or submission.

## Implementation preflight: student evaluation persistence

**Safe first slice:** the existing local Vitest harness can support a test-first, detached versioned API-envelope contract, with no database, backup, or production access: add boundary tests in `src/lib/validation/apiSchemas.test.ts` and a strict CD-07 schema in `src/lib/validation/apiSchemas.ts` (instrument/version discriminator, assignment revision, exactly 20 integer answers 1–5, optional/null comment ≤2,000; reject extras and all N/A encodings). Preserve `EstudianteEvaluacionSchema` as the general 19-answer contract. Keep this slice detached: it validates shape only, does not authorize a student/group, select an instrument, or write. Vitest is the concrete runner (`npm run test:run -- src/lib/validation/apiSchemas.test.ts`); this is a bounded unit well below 400 authored changed lines.

For the first persistence-specific test-first slice, existing migration-contract tests such as `src/lib/testCycleDeletionFkClosureMigration.test.ts` show the local pattern: Vitest reads a proposed SQL file and asserts explicit invariants without connecting to Postgres. A future dedicated test can target a new additive student-response migration under `supabase/migrations/`, asserting separate versioned storage, 20 non-null 1–5 values, comment ≤2,000, no destructive/history-changing statements, and no loosening of the legacy 19/500 path. Such static tests are not SQL execution, concurrency, RLS, or grants proof. **Do not author the persistence migration yet:** first obtain complete, current schema/constraint/FK/trigger definitions and confirm migration-ledger state; stop rather than guess column types, dependencies, or compatibility behavior if any are incomplete. The checked-in `043_native_student_scale_1_to_5.sql` is destructive history and must never be run, replayed, recreated, or adapted; `103_fix_student_evaluation_1_5_constraints.sql` is also not proof of deployed state.

**Trusted boundaries and blockers:** `src/pages/api/estudiante/evaluaciones.ts` derives the session user, but its current rate-limit lookups are not authorization; its RPC call and client-provided `grupo_id` cannot establish eligibility. `src/lib/studentEvaluations.ts` currently has no instrument identity, and `src/services/scoring.ts` currently coerces native scores to `native-19-v2`. A secure eventual write must derive student identity from `auth.uid()` in a database-enforced RPC, check role, active enrollment/group/teacher/cycle and server-selected CD-07 version there, and atomically store response plus the shared one-time control/audit. Never accept a student identity from the client or let application prechecks substitute for DB enforcement. The reported schema-only evidence observes exactly-19 answers / 500-character comments in the general RPC, shared `encuesta_control_envio` UNIQUE(student,group,cycle) plus audit trigger, and RLS enabled on six tables; it does not prove effective grants/runtime behavior or reconcile checked-in SQL with deployment.

**Concurrency and bypass:** competing general/CD requests must rely on the shared unique control and transactional response+control writes, not an API “already submitted” precheck. The existing 19-answer RPC remains a bypass risk: it must reject a group currently assigned CD-07 at the database boundary, while CD-07 persistence must contend on that same cross-version control. Verify locks/conflict handling and rollback under concurrent submissions in authorized staging before activation; static Vitest checks cannot establish those properties. TEST-CD stays a separate disabled, noninstitutional fixture path; the 20 CSV-present group mapping and its digest remain as recorded above, and Pending CSV rows are not answers or enrollment evidence. General 19/history remain unchanged; CD has no N/A and comment ≤2,000. No production DB write, deploy, fixture write, backup-dependent change, or activation is authorized while implementation/evidence is incomplete. Stop if schema definitions, migration state, runtime/grant behavior, trusted identity or shared-control semantics cannot be verified; no backup requirement is waived for a later production deployment.
